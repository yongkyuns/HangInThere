# Native Android client

Home offers camera counting, a workout log and workout history. The log supports custom exercises, lb/kg loads, quick entry, tap counting with undo, editing and per-exercise progress. Calendar/List views include real week/month layouts, date navigation and historical workout markers. Screens follow the system light/dark theme.

The camera defaults to automatic exercise selection. Pull-ups use `OverheadPullUpWorkout`; dips use `RelativeDipWorkout`, the same common controllers used by iOS. Grip metadata is optional; neither bars nor rails are required. Use a fixed phone at chest/shoulder height, aimed level from the front or rear, with measurable arms. Counts describe observed image cycles; depth/lockout form remains unverified.

Video review consumes one uncut source pass, including setup, rest, release and subsequent sets. Recorded video assumes fixed phone attitude and still requires independently measured background stability. Historical apparatus-based replay helpers live in instrumentation tests only.

## Build

Use JDK17, Android SDK36 and the checked-in Gradle8.13 wrapper. Tool/plugin/artifact versions are explicit. MediaPipe0.10.32 is checksum-verified before packaging and includes actual ARM32/ARM64/x86/x86_64 JNI, each independently inspected with16KiB ELF LOAD alignment. Earlier0.10.26.1 lacked emulator JNI and is not used. Download the official Heavy model with its verified SHA256:

```
python3 scripts/prepare-mediapipe-model.py --output android/app/src/main/assets/pose_landmarker_heavy.task --metadata build/android-model.json
./gradlew :android:app:assembleDebug
```

The model is ignored. Normal instrumentation uses only the pinned public fixtures prepared by `scripts/prepare-android-fixtures.py`. An explicitly authorized imported-recording run can temporarily prepare ignored private assets through the separate encrypted workflow described below.

## Boundaries and ownership

* Calendar boundaries, week/month navigation, log validation, exercise matching, prefill, load conversion, timed rest, logged progress and camera-set linking live in common Kotlin. iOS and Android supply native views, date/number formatting, persistence and system integrations. Typed results never invent timing or camera measurements.
* `shared` contains source-owned athlete association, motion counting/progress, automatic exercise selection, stability policy and set lifecycle. `WorkoutSetPresentation` supplies phase-time demand, recovery previews, comparable-rep tempo and keyframe timestamps to both platforms. The reciprocal background pixel sampler and geometry are shared C++; bitmap ingress stays native. Apple Vision and Android MediaPipe body estimates remain different, so shared rules alone do not establish physical-device accuracy parity.
* Historical apparatus acquisition remains available for explicit diagnostics and compatibility. The common module has no Android or pose SDK imports and exports static `WorkoutCore` iOS frameworks.
* `CanonicalPixels` is the sole camera/video orientation and scaling boundary: upright top-left pixels, maximum1280 dimension, no front-camera reflection or left/right swapping. Even-aligned YUV420 crops pack exact row/pixel-stride samples into I420. BT.601 limited uses OpenCV's fast conversion; BT.601 full and BT.709 full/limited use a native float matrix before final RGB clipping. Odd crop origins or dimensions use the same selected matrix with scalar sampling. Native differential tests bound RGB rounding differences to two levels and preserve caller plane positions. `VideoTransform` is shared by drawing and manual tap mapping.
* `PoseEstimator` maps33 MediaPipe landmarks to the canonical19-joint schema. Derived neck/root use midpoint positions and the weaker parent score. Raw minimum visibility/presence is recorded explicitly; it is not calibrated to Apple Vision confidence. CPU Heavy and numPoses2 are pinned; multiple visible people fail the shared single-athlete gate.
* `ObservedEdges` applies a 5×5 Gaussian filter and extracts actual OpenCV Canny contours only in bounded grayscale pose-guided crops; pose/display pixels retain their original values. The shared bounded fitter operates on observed pixel samples; it never invents a between-wrists bar/rail. Dip acquisition supports independently witnessed rails or a separately validated paired straight bar near both grips. Its geometry ranking is not semantic confidence.
* `SceneRegistration` freezes an associated athlete's camera frame, then measures reciprocal peripheral background correspondences using the shared Apple/Android sampler. Fresh scale and translation consensus plus source-time epoch evidence are mandatory; missing observations stay unknown. Android rotation-vector samples independently qualify rotation and absolute tilt. A bounded capture-time history selects nonfuture sensor samples. Cameras without Android's REALTIME timestamp contract offer video evaluation.
* `AnalysisPipeline` serially owns model/native resources, athlete selection and `MotionWorkoutRuntime`. It persists draft deltas and each completed set, and revokes preparation when camera context changes.

* `VideoFrames` selects MediaExtractor/MediaCodec for SDR and a bounded software HEVC Main10 decoder for explicitly supported BT.2020 HLG/PQ inputs, including the compatible Dolby Vision profile8 HLG base layer. Source PTS are never inferred from frame indices, seek intervals, decode latency or wall time. Track rotation applies once. Output images, buffers, codecs and software readers are released deterministically. Replay consumes the full source once, preserving multiple sets and source timestamps. Replay's identity quaternion is a virtual fixed-phone assumption, clearly separate from live sensor evidence; actual background registration is still required.
* `VideoColorPolicy` reads source and actual per-buffer decoder standard/range/transfer. SDR supports BT.601/BT.709 full/limited range; missing legacy metadata uses the declared BT.601-limited assumption. The software HDR adapter verifies every actual 10-bit input and mapped BT.709 output frame. Unsupported HDR formats, unknown/linear transfer and unconverted BT.2020 fail explicitly. Any HDR reaching the MediaCodec path still requires its API31+ tone-map negotiation and verified SDR output; a request alone never proves conversion. See [HDR mapping, dependencies and native qualification](../docs/ANDROID-HDR.md) and the [current original-video results](../docs/ANDROID.md#authorized-recording-checkpoint).

## Qualification limits

Historical apparatus instrumentation reports exact decoded PTS, decoded frame count, observed MediaPipe movement counts on reviewed fixed edges, actual contour detections, pose/decode/contour/scene latency distributions plus separate historical Auto replay acquisition and full pipeline/display-copy timings and process/native/Java memory. `pipelineWithDisplayCopyLatencyMillis` includes decoder read, canonical pixel conversion, inference, contours/registration, shared runtime and display copy; it excludes model initialization and the final EOF read that returns no frame. Reports are written under app external-files `evaluation/` even when count parity fails. A fixed-edge fixture count is not a proof that production Auto setup succeeds on that view. JVM shared-engine oracle parity separately isolates policy equivalence from differences in body-pose backends.

CPU/emulator wall time is not phone frame-rate, thermal, battery or camera qualification. Front-camera hardware, sensor timebase alignment and background texture sensitivity need physical Android coverage before claiming full live/performance parity. Replay setting/grip changes restart the full cached video source on a new generation; completion closes the actual counter. Completed replays expose Evaluate again. Exercise/grip/camera changes are disabled during live sets so the selected exercise remains fixed. UI instrumentation captures the real app before assertions, including failures. No fallback fabricates stable registration evidence.

## Authorized imported recording evaluation

`ImportedRecordingEvaluationTest` is opt-in: normal public jobs skip it when `generated/private-evaluation/manifest.json` is absent. Its schema is `{schemaVersion:1,cases:[...]}`. Each case supplies a neutral `recording_...` ID and `.mp4` asset name, SHA256, `frames`, exact integer `sourcePtsMicroseconds`, `exercise`, `side`, `expectedMovements`, source-reviewed `referenceEdge` and its `referenceImageSize`. Multiple side cases can share an asset. Any prepared derivative must disclose its source and transformation in the encrypted manifest and retain the full source timeline.

The test reuses the historical apparatus evaluator `NativeReplayEvaluator`; it does not qualify the current motion-based production route. Each case runs full Auto acquisition/review with actual pixels and scene registration, plus a separate manual fixed-edge counter diagnostic over every source frame. Both runs verify exact PTS and full frame coverage. The manual diagnostic isolates pose/counting from setup and does not claim manual UI or apparatus acquisition parity.

All imported reports, pose/snapshot traces and detailed errors stay in app external-files `private-evaluation/`. Console/JUnit failures contain only neutral IDs, counts and completion status. Temporary cache copies are deleted. The caller must encrypt these derived outputs before upload, isolate decryption keys from pull-request code, disable build-cache publication and avoid publishing the test APK or intermediates: the test APK embeds the private assets. Private source media, manifests, plaintext reports and keys remain ignored and must never be committed or attached to public artifacts.

`MotionPipelineReplayTest` accepts an explicit `motionManifest` instrumentation argument pointing to an app-readable local manifest. It runs private full sources through the current native Auto pipeline and retains per-frame poses/camera verdicts, records and failures in app files. `Evaluation/MotionCameraReplay.swift` provides fresh Apple-host observations; `MotionNativeReplayTests` replays identical observations through the common Android lifecycle to isolate rule parity. These are development comparisons, not physical-device qualification. No private media is bundled or uploaded.
